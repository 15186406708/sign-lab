# 设计说明 · sign-lab

这份文档记录**为什么这么设计**，以及在面试里怎么讲。README 讲「怎么用」，
这里讲「为什么」。

---

## 1. 威胁模型：为什么必须自建服务端

任何签名逆向的练习都存在一个绕不开的问题：**目标站点的代码、数据、接口都不属于你**。
即使只是练习，把「某个真实站点的绕过代码」放进公开仓库也是错的——
对应的是刑法第 285 条第 3 款那条线，判例里已经有人因此获刑。

所以本靶场的做法是：**自己造一个目标**。

| 真实场景里的东西 | 本靶场里的对应物 | 合法性 |
|---|---|---|
| 目标站点的签名接口 | `server/app.py`，作者自己写 | 自己的服务器 |
| 目标站点的混淆 JS | `server/signer.obf.js`，作者自己生成 | 自己的代码 |
| 目标站点的限流风控 | 按 IP 的令牌桶 + 429 提示 | 自己的策略 |
| 目标站点返回的业务数据 | `make_items()` 程序生成的假数据 | 无真实数据 |
| 第三方 SDK、真实凭据 | **不存在** | — |

结论：这份仓库能公开，不是因为它「脱敏做得好」，而是因为它**从根上就没有第三方目标**。
这是「GitHub 上放能力、不放目标」这条原则的具体落地方式。

## 2. 为什么把签名藏起来，而不是直接写在文档里

如果盐是明文，这个项目就退化成一堆 HTTP 代码，学不到任何东西。

真实目标里，签名算法的可读性已经被刻意破坏了。所以本靶场也照着真实的破坏手法做了四层：

| 层 | 手法 | 对应真实目标的什么做法 | 还原它需要的能力 |
|---|---|---|---|
| 1 | 盐散在 80 字符的字符串表里 | 字符串数组混淆（最常见的一层） | 找到「表 + 下标」这个结构 |
| 2 | 表内容是异或编码的数字，运行期 `fromCharCode(code ^ mask)` | 字符串加密 / 数组解密函数 | 识别解码函数，把码表和掩码都挖出来 |
| 3 | 下标写成 `(0x100 >> 5)` 这类表达式 | 常量折叠 | 静态求值，而不是猜 |
| 4 | 掩码本身也是表达式 `(0x2 ^ 0x3e)` | 同样的常量折叠，用在密钥上 | 变量回溯：从变量名找回它的赋值 |

第 2 层是关键：**它让「把 `\x6a` 读成 `j`」这种纯体力活失效**。
必须理解解码函数在干什么，才能自己算出来。

## 3. 为什么用 AST 白名单求值，而不是 `eval`

下标表达式是**目标（这里是靶场）控制的字符串**。哪怕这里的 JS 是自己写的，
用 `eval()` 求值也是坏习惯：一旦这套代码被复用到真实目标上，
你就是在自己的机器上执行别人写的任意表达式。

`recover.safe_int_eval` 只放行这些 AST 节点：

```
Expression / Constant(int) / UnaryOp(USub) / BinOp(+ - * | ^ & << >>)
```

函数调用、属性访问、下标、名字引用、比较、Lambda 全部拒绝。
一个反向工程工具的执行边界，应该由分析者定义，而不是由被分析对象定义。

## 4. 为什么走「复算」而不是「执行 JS」

这是整个项目的核心取舍，也是最值得在面试里讲的一段。

**执行 JS（Node / execjs / 浏览器）的代价：**

* 需要 Node 运行时，版本一变行为可能变；
* 真实目标的 SDK 常有反调试、环境检测、异步初始化，抠出来跑的成本远高于读懂它；
* 异步生成的签名，往往要开浏览器、保会话、维护 cookie 龄期；
* 进程常驻、内存占用高，规模化采集时是瓶颈。

**复算的收益：**

* 主流程零第三方依赖，没有 Node 版本漂移；
* 无会话态、无进程常驻，天然适合并发与长期运行；
* 签名算错时能逐段打印中间值定位（见下面第 6 节的对齐手段）；
* 面试里能讲清楚「我把它算出来了」，比「我把 JS 跑起来了」值钱得多。

**代价也要说清楚**：复算要求你真正读懂算法。读不懂的时候，
`tests/parity_check.py` 就是安全网——两侧逐组比对，偏了就立刻暴露。

## 5. 服务端为什么刻意「话多」

真实的登录 / 数据接口返回 `401` 时，多数只给一句「签名错误」。
本靶场在 `401` 里**额外回带了服务端算出的规范化查询串**。

这是故意的：它让「签名算错了」这件事变成一个可对齐的问题，
而不是一个只能靠猜的黑盒。对应真实的排错流程：

```
1. 固定时间戳和 nonce，消除随机变量
2. 用同一组输入，在浏览器侧和 Python 侧分别打印中间值
3. 逐段比对：拼接顺序 → 参与字段 → 编码方式
4. 定位第一处不一致的位置，只改那一处
```

三段里最常见的是**拼接顺序**和**编码方式**（参数值要不要再 URL 编码、
空格编码成 `%20` 还是 `+`）。规范化串一回带，这类问题通常一眼就能看出来。

## 6. 限流治理：为什么 429 不能抛异常

靶场服务端是令牌桶：容量 3，之后每 2 秒恢复 1 个令牌，被拦时明确告诉你要等几秒。

客户端 `ratelimit_kit.parse_retry_after` 的优先级是：

```
正文文本（正则找「N 秒」） → retry_after 字段 → Retry-After 头 → 默认值
```

**正文优先**，这是实战教训：真实服务端经常只在 `errmsg` 里写「请在 N 秒后重试」，
`Retry-After` 头反而是缺的。

**为什么不能把 429 抛成异常交给上层或框架重试**：
框架的自动重试会立刻连点。每一次连点都会把令牌桶的时间轴往后推，
于是恢复时间从 2 秒变成十几秒，最后变成「越重试越打不开」。
正确的做法是**原地退避**：读服务端给的时长，原地睡够，再重试**同一个请求**。

另外一个细节：等待时长要加**随机抖动**。多个客户端如果同时被拦、同时醒来，
会再次撞在一起，抖动把它们的相位错开。

## 7. 「能长期跑」还差什么，这里补齐了

只做到「签名算对、请求发出去」还是 demo。本项目的 `collect.py` 补了三件事：

| 问题 | 做法 |
|---|---|
| 跑到一半断了，要从头再来 | `checkpoint.json` 记已完成页，且**只前进不后退**（用 `--restart` 重跑旧页也不会把它写回去） |
| 重复跑同一页写出重复行 | 落盘前按 `id` 去重，去重集合从已存在文件里重建 |
| 数据写了一半，进度却已推进 | 先 `flush()` + `fsync()` 落盘，**再**推进 checkpoint；checkpoint 用「写临时文件 + 原子替换」 |

这三条各自都很小，但合起来决定了「这个脚本能不能无人值守地跑一整晚」。

## 8. 可讲的技术点清单（面试用）

1. **定位签名入口**：网络面板筛出目标请求 → 看哪些参数在变 → 断点/hook 回溯调用栈。
2. **判断同步还是异步**：异步就不抠代码，走脚本执行；同步才值得复算。
3. **字符串表还原**：`表[下标表[i]]` 这个结构比变量名可靠得多，改名不影响定位。
4. **解密函数识别**：`fromCharCode(code ^ mask)` 是常见形态；掩码可能是变量，要回溯赋值。
5. **常量折叠求值**：用 AST 白名单，不用 `eval`。
6. **两侧对齐排错**：固定随机量 → 打印中间值 → 三段比对（顺序、字段、编码）。
7. **限流治理**：全局限速 + 读服务端提示 + 原地退避 + 抖动；不把 429 抛给框架。
8. **长期运行**：断点续跑、幂等落盘、先落盘后推进进度。

## 9. 后续要补的关卡

按「离真实目标有多远」排序：

1. **POST body 签名**：现在只有 GET query，真实场景大量是 JSON body + 时间戳 + 签名头。
2. **多段盐**：盐按时间片轮转，或与设备指纹拼接（`nonce + 盐 + 指纹 + query + ts`）。
3. **会话态**：先取 `token`，再用 token 参与后续签名（引入依赖链）。
4. **验证码环节**：在签名之前插一道 challenge，练习「校验通过才开始签名」的编排。
5. **控制流平坦化**：把入口函数做 `while + switch` 打散，逼出结构化反混淆能力。

每补一关，`tests/parity_check.py` 的用例集都应该同步扩充——
**测试是复算路线的安全网，不是装饰。**
